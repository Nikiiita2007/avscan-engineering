# Этап 9: UX/UI дизайн

Статус: только дизайн. Интерфейс не реализован, код не менялся. Документ описывает локальную веб-панель поверх готового HTTP-API оркестратора (этап 6) и список изменений API, без которых панель не построить.

## 1. Цель и границы
- Дать человеку без терминала три вещи: увидеть состояние модулей, запустить проверку (лог, каталог проекта, pcap) и смотреть находки в реальном времени.
- Панель работает только на этом компьютере: оркестратор слушает loopback. Удалённого доступа, учётных записей и ролей нет.
- Панель не заменяет CLI. Всё, что она делает, делается теми же запросами, что `curl` и `orchestrator exec`.
- Вне границ: редактирование манифестов и `orchestrator.json`, просмотр файлов, управление C++ антивирусом.

## 2. Пользователи и задачи
| Кто | Что нужно |
|---|---|
| Владелец компьютера | Понять за пять секунд, всё ли в порядке; запустить проверку каталога; увидеть, что найдено и насколько это серьёзно |
| Администратор | Перезапустить упавший модуль, увидеть причину отказа, проверить, что включена авторизация |
| Разработчик модулей | Видеть сырые события шины, отправлять команды и события вручную |

Главная задача первого экрана: ответить на вопрос «нужно ли мне что-то сделать прямо сейчас».

## 3. Что даёт API сейчас
| Экран или элемент | Источник | Что известно |
|---|---|---|
| Список модулей | GET /modules | id, state (starting, running, restarting, stopped, failed), restart_attempt, error |
| Живая лента | GET /events (SSE) | событие module_event с полями topic, source, data; событие lagged с полем dropped; keep-alive раз в 15 с |
| Старт, стоп | POST /modules/{id}/start и /stop | 202, 404, 409 |
| Запуск проверки | POST /modules/{id}/command | 200 с ok и error, либо 404, 409, 429, 502, 504 |
| Событие от хоста | POST /events | 202 с receivers, либо 400 |
| Проверка связи | GET /health | открыт и без токена |
| Авторизация | заголовок Authorization: Bearer | ответ 401 с WWW-Authenticate |

У находок есть общие поля rule и severity (уровни critical, high, medium, low); остальные поля у модулей разные и должны быть подтверждены перед вёрсткой карточки.

## 4. Экраны

### 4.1 Обзор (главный экран)
```
+---------------------------------------------------------------------+
| AVScan                  [o] Подключено 127.0.0.1:8787   [Настройки] |
+---------------------------------------------------------------------+
| Итог: 1 модуль требует внимания              [Показать]             |
+---------------------------------------------------------------------+
| Модули                                                              |
| +-------------+-----------------+---------------------+-----------+ |
| | Модуль      | Состояние       | Последняя находка   | Действия  | |
| +-------------+-----------------+---------------------+-----------+ |
| | log_hunter  | [v] Работает    | HIGH ssh-bruteforce | Проверить | |
| | vuln_scanner| [!] Сбой        | -                   | Запустить | |
| |             | cannot spawn... |                     |           | |
| | net_analyzer| [-] Остановлен  | -                   | Запустить | |
| +-------------+-----------------+---------------------+-----------+ |
| Лента находок                                    Фильтр: [Все v]    |
| 21:14  HIGH     log_hunter  ssh-bruteforce  203.0.113.5            |
| 21:13  MEDIUM   net_analyzer suspicious-port 10.0.0.2:4444         |
+---------------------------------------------------------------------+
```
- Верхняя полоса «Итог» заменяет обзорные диаграммы: она называет число модулей в состояниях failed и restarting и число находок уровней critical и high за сессию. Если всё хорошо, там написано «Всё работает» без декоративных элементов.
- Состояние показывается значком, словом и цветом одновременно.
- Причина сбоя (поле error) видна в строке, длинный текст сворачивается.
- Лента сортируется по важности, затем по времени; новая запись не сдвигает строку, на которую наведён курсор.

### 4.2 Модуль
- Заголовок: имя, состояние, номер перезапуска, кнопки «Остановить» и «Запустить» (доступна только одна из них по состоянию).
- Блок «Проверка»: форма под команду модуля. log_hunter: поле путей (log.hunt, paths). vuln_scanner: поле путей (vuln.scan_files, paths). net_analyzer: поле путей pcap (net.analyze, pcap_paths). Один путь на строку; рядом видно, из каких корней модуль принимает пути (см. раздел 9).
- Результат отправки: кнопка блокируется на время запроса (до 30 с), рядом счётчик ожидания и кнопка «Отмена ожидания» (отменяет только ожидание в браузере, а не работу модуля).
- Ниже лента событий только этого модуля.

### 4.3 Находки
- Таблица: время, уровень, правило, модуль, краткое описание. Строка раскрывается в панель «Почему это важно»: данные события как есть, без пересказа.
- Фильтры: уровень, модуль, правило, текст. Выбранные фильтры видны в адресной строке.
- Находки хранятся в памяти страницы (до 1000 записей) и теряются при перезагрузке; это нужно сказать пользователю прямо (см. раздел 6).

### 4.4 Настройки
- Адрес API и токен. Токен вводится в поле типа password, хранится только в памяти вкладки и не попадает в адрес и в журнал.
- Индикатор «Авторизация: включена или выключена» по ответу сервера. Если выключена, баннер: «Любая программа на этом компьютере может управлять модулями».
- Раздел «Для разработчика» (свёрнут): ручная публикация события (topic, data) и сырая лента шины.

## 5. Состояния и тексты
| Ситуация | Что видит пользователь | Что можно сделать |
|---|---|---|
| Нет связи с API | Баннер «Нет связи с оркестратором 127.0.0.1:8787» | Повторить, изменить адрес |
| 401 | «Нужен токен или он неверен» | Открыть настройки |
| Модуль failed | Строка помечена, показана причина | Запустить |
| Модуль restarting | «Перезапуск, попытка N» | Подождать, остановить |
| 409 при старте или стопе | «Состояние уже изменилось» и обновление списка | Нет |
| 429 | «Очередь команд модуля заполнена» | Повторить позже |
| 502 | «Модуль завершился, не ответив» | Проверить состояние модуля |
| 504 | «Модуль не ответил за 30 с; работа могла продолжаться» | Смотреть ленту событий |
| ok = false | Текст error из ответа, без перефразирования | Исправить пути, проверить корни |
| Событие lagged | В ленте метка «Пропущено N событий» | Нет |
| Пустая лента | «Находок нет с момента открытия панели» | Запустить проверку |

Сообщения о результатах действий не забирают фокус и не должны требовать закрытия.

## 6. Реальное время
- Встроенный в браузер EventSource не умеет отправлять заголовок Authorization, а /events при включённом токене его требует. Значит панель читает SSE через fetch и разбирает поток сама или готовой обёрткой (например, fetch-event-source). Использовать токен в адресе нельзя: он попадёт в историю и журналы.
- SSE у нас live-only: после обрыва события не повторяются. Панель при переподключении вставляет в ленту метку «Связь прерывалась, события могли быть пропущены» и сразу перечитывает GET /modules.
- Состояние модулей обновляется опросом GET /modules раз в 5 с и после каждого действия; SSE несёт только события модулей.
- Переподключение с растущей паузой (1, 2, 4, 8, максимум 30 с) и видимым индикатором.

## 7. Визуальный язык и доступность
- Уровни важности кодируются дважды: цветом и текстовой меткой (CRITICAL, HIGH, MEDIUM, LOW) плюс значок разной формы. Цвет никогда не единственный носитель смысла.
- Красный только для critical и failed. Если красным залит весь экран, иерархии нет. Акцентные цвета интерфейса не пересекаются с палитрой уровней, чтобы кнопка не выглядела как тревога.
- Серьёзность и уверенность разделяются: если у находки есть оценка уверенности, она показывается отдельно.
- Две темы, светлая и тёмная; контраст проверяется для каждой палитры отдельно, а не получается инверсией.
- Динамические сообщения (итог, результат команды, переподключение) лежат в контейнере с role=status и aria-live=polite, созданном в разметке до добавления текста. role=alert только для critical и потери связи, потому что лишние assertive-регионы считаются ошибкой.
- Всё управляется с клавиатуры; видимый фокус; таблицы с настоящими заголовками; минимальная цель нажатия 24 px.
- Лента не должна прокручиваться сама, если пользователь прокрутил вверх; кнопка «К новым» возвращает к концу.
- Текст интерфейса на русском, термины вроде rule и severity в таблицах не переводятся, чтобы совпадать с данными.

## 8. Безопасность интерфейса
- Запросы start и stop не имеют тела. Если токен не задан, любая веб-страница, открытая в том же браузере, может отправить на 127.0.0.1 такой POST как простой запрос и остановить модуль. Защиту от этого даёт токен; для режима с панелью токен нужно сделать обязательным.
- Нужна проверка заголовков Host и Origin на стороне сервера (защита от DNS rebinding и чужих страниц): допускаются только адреса loopback и собственный источник панели.
- Панель отдаётся самим оркестратором с того же адреса (тот же origin), без CORS и без внешних скриптов, шрифтов и CDN; ресурсы встроены в бинарник.
- Токен не пишется в localStorage, адрес, журнал и сообщения об ошибках.
- Содержимое событий выводится как текст, не как HTML (в событиях есть строки из логов, которыми управляет атакующий).
- Права панели равны правам токена; отдельных ролей нет.

## 9. Пробелы в API
Без этого панель будет угадывать или показывать неполные данные.
1. GET /modules должен возвращать capabilities и command_roots модуля, чтобы форма знала команды и разрешённые каталоги, а не хранила их в коде.
2. История находок. SSE без повторов теряет всё при перезагрузке; нужен ограниченный буфер на сервере (например, последние 500 событий) и маршрут чтения.
3. Описание аргументов команд (имя поля, тип), чтобы форма строилась автоматически; сейчас имена paths и pcap_paths у модулей разные.
4. Проверки Host и Origin и обязательный токен в режиме панели (раздел 8).
5. Раздача статических файлов панели оркестратором.
6. Единый формат находки у трёх модулей (общие поля, время, уровень, описание); сейчас подтверждены только rule и severity.

## 10. План реализации
| Часть | Содержание | Проверка |
|---|---|---|
| 9.1 | Пробелы 1, 4, 5 в API; страница-заглушка по адресу /ui | тесты маршрутов; 403 на чужой Origin и Host |
| 9.2 | Обзор и модуль: список, старт и стоп, форма проверки | ручная проверка по сценариям раздела 2 |
| 9.3 | Живая лента на fetch, переподключение, метки пропусков | тест с обрывом соединения |
| 9.4 | Находки, фильтры, тёмная тема | проверка контраста и клавиатуры |
| 9.5 | История на сервере (пробел 2), единый формат находок (пробел 6) | тесты формата |

Критерии приёмки этапа:
- Сценарии «запустить проверку каталога», «перезапустить упавший модуль» и «найти самую серьёзную находку» проходятся без терминала.
- Каждый статус и каждая ошибка из раздела 5 имеет текст и проверяется тестом или ручным пунктом.
- Панель работает без внешней сети.
- Нет информации, переданной только цветом.
- Чужая веб-страница не может остановить модуль при включённом токене и при выключенном получает 403.

## 11. Открытые вопросы
- Нужна ли панель на Windows и в каком браузере её проверять.
- Делать ли токен обязательным только для панели или для всего API.
- Достаточно ли ограниченной истории в памяти или нужно хранение на диске.
- Показывать ли находки сырым JSON для разработчика всегда или только в режиме разработчика.
- Какой технологический вариант выбрать: статические HTML, CSS и JS без сборки (проще проверить и встроить) или фреймворк со сборкой (удобнее для сложных экранов).
